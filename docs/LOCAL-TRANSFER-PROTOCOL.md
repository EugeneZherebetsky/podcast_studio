# Local transfer protocol v1 — proposed security contract

Status: **design only, not independently reviewed or implemented**. This specifies T17/T19; it does not authorize enabling a listener. USB import is independent. Owner approval covers an optional local-only listener, Android native module and expo-secure-store; changes to shared, SQLite or package schemas, or a non-loopback default, require separate approval. The management server remains loopback-only; never expose its legacy pairing, bearer API, sync routes or a proxy to it. No playback progress or vocabulary leaves the phone.

## Trust and identity

The user physically views a QR on the PC's local UI and scans it directly with the phone while controlling both devices. The PC UI must be reached locally, not from a remotely served or forwarded page. This is the authenticated out-of-band channel: no screenshots sent over chat, discovery, DNS, or network-delivered QR. An attacker who can replace the local UI/QR, control an endpoint, or observe and race a legitimately displayed QR is outside this ceremony's guarantee; PC acceptance and short lifetimes reduce, not eliminate, that risk. Do not proceed if physical provenance is uncertain.

The PC creates an app-dedicated self-signed server certificate and private key using a secure OS RNG. The certificate is a CA:false server-auth leaf with a DNS or IP subjectAltName exactly matching the selected connection hostname or literal IP, supported key/signature algorithms, and bounded validity (at most 1 year). Keep the private key in an OS-protected, user-only store, never in the QR, logs, repository, or a backup without equivalent protection. If secure generation/storage or certificate validation is unavailable, keep transfer off. The QR v1 contains only version, selected HTTPS host and port, full DER certificate (bounded to 8 KiB), SHA-256 of its DER, a random 128-bit pairing ID and a random 256-bit single-use pairing secret; encode binary values as unpadded base64url. It expires 120 seconds after PC creation, measured by the PC's monotonic clock. The phone recomputes the fingerprint from the certificate, shows the full fingerprint and endpoint for confirmation, and requires an explicit user confirmation. Do not log, persist, or share the QR or its secret. Cancel or expiry invalidates it.

For each connection, the Android native client creates an isolated TLS context whose only trust anchor is the exact QR-provisioned certificate, and performs normal X.509 chain/signature, validity, server-auth usage, and endpoint identification checks, plus a constant-time SHA-256 comparison of the actual leaf DER to the approved fingerprint during the handshake. Treat the certificate as a specifically provisioned trust anchor, not as a general public CA; validate leaf constraints explicitly even where the TLS library omits anchor validity/usage checks. Reject malformed chains, unexpected intermediates, absent SAN, wrong DNS/IP SAN, expired/not-yet-valid certificate, unsupported algorithms or mismatched pin. Require TLS 1.2 or later, disable early data and renegotiation; prove private-key possession in the handshake. Never use trust-all, a permissive hostname verifier, post-request pin checking, global TLS overrides, or fallback HTTP/system trust. Complete all checks before writing any HTTP bytes, including the pairing secret or bearer token. If the platform cannot enforce this ordering, stop. This is certificate pinning plus ordinary verification under the explicitly provisioned trust anchor, not public-CA verification.

## Admission and lifecycle

The user explicitly enables the separate listener for a session and selects one active private home Wi-Fi interface and concrete unicast address; bind only that address, not wildcard or loopback management socket. The PC firewall must be configured by the user to permit that exact interface and port only on the intended home network; no automatic router mapping, port forwarding, relay, tunnel or public exposure. Default off after restart, disable or network/interface change. Accept only traffic arriving on the selected interface from a unicast on-link peer; IPv4 and IPv6 must each satisfy interface, address, route and firewall checks, including scoped IPv6 handling. Reject forwarded/routed traffic when it cannot be established as local; private ranges or a subnet alone are insufficient. Disable VPN, proxy, cellular and other interfaces for this path; if interface/route provenance or firewall policy cannot be reliably verified on a platform, do not enable it. Admission cannot prove that a hostile on-link device is trusted, nor defeat a malicious router/bridge; TLS and acceptance remain necessary.

On Android, require user-selected active Wi-Fi, no VPN and a direct network-bound socket; resolve a DNS name once on that network, connect only to a vetted on-link address, retain the original hostname for SNI and SAN checks, and do not re-resolve mid-connection. For IP literals check an IP SAN, not a DNS SAN. Reject link-local ambiguity, invalid scope, multicast, loopback and public addresses. On network, interface, route, DNS or address change, close sockets and cancel in-flight operations; require fresh admission and full TLS verification before reconnecting. A new address is not silently trusted: if the SAN no longer matches, stop and perform a fresh physical ceremony with a newly provisioned certificate. No automatic discovery is trusted as identity. Disable all HTTP redirects, proxy/PAC/environment proxy use, connection coalescing across origins, cookies and credential forwarding. Reject every 3xx, including same-origin. Never retry a secret to another address without the complete admission and TLS checks.

## Pairing and authorization

1. PC enables the listener and presents one QR; at most one pending ceremony exists. Phone scans, confirms and validates it, then establishes the pinned TLS connection as above. Only then `POST /v1/pair` with JSON `{pairingId, pairingSecret, deviceName}` (name 1–64 printable characters). No token is supplied. PC verifies the ID, secret and 120-second deadline in constant time, atomically consumes the secret, and creates a pending request with a random 256-bit one-use poll capability. It displays the untrusted device name and a six-digit comparison code. Both sides compute it from the first 32 bits of SHA-256 over UTF-8 `podcast-transfer-v1` followed by raw pairing ID and secret, interpreted big-endian modulo 1,000,000 and zero-padded. User checks it on both screens and explicitly accepts or rejects on the PC. Name and code alone are not identity proof. The response contains the poll capability only over the verified TLS connection; never a URL or log.
2. The phone polls `POST /v1/pair/result` with `{pairingId, pollCapability}` on newly verified connections if needed. Pending is `202`; rejection, cancellation, expiry or mismatch gives a generic failure and invalidates capabilities. Approval is allowed only while the original 120-second window remains open. On explicit acceptance the PC creates a distinct 256-bit random bearer token, scoped solely to `episode:read`, expiring after 30 days; its first successful result response returns it exactly once and consumes the poll capability atomically. Lost response means no recovery of the token: revoke the orphan record and start a new ceremony. Token issuance, consumption, denial and revoke operations must serialize; restart invalidates all pending ceremonies. A concurrent or replayed request never receives another token. A rejection or timeout never issues one.
3. The phone writes the token and pinned certificate/endpoint to expo-secure-store before use, with Android backup excluded; no AsyncStorage, SQLite, logs, clipboard, URL, analytics or insecure fallback. If secure write fails, do not use it; tell the user to revoke the orphan on the PC. Keep pairing secret and poll capability only in memory and erase on completion/cancel. Store PC token verifier as SHA-256 of the high-entropy token, scope, expiry, random device identifier and user-visible device label in an access-controlled local store, not plaintext token. Never store verifier, credentials or identities in the existing shared/SQLite contract without separate approval. Keep security decision records locally for at most 30 days, without secrets, IP addresses or episode contents; delete expired records and provide local deletion. No cloud backup or telemetry.
4. Each read independently authenticates `Authorization: Bearer <token>`, checks expiry, revocation and exact scope before looking up the resource, and returns generic `401` on invalid credentials. Allowed routes only: `GET /v1/episodes`, `GET /v1/episodes/{episodeId}`, `GET /v1/episodes/{episodeId}/audio` for finished episodes. List returns only minimal metadata needed for selection; metadata and audio use the existing package contract. IDs are opaque, length bounded and never filesystem paths; resolve only server-owned finished episode records under the episode root. Deny all other methods/routes, uploads, write operations, admin, legacy token and progress/vocabulary access. No CORS, browser cookies or credential-bearing query parameters. Range downloads, if supported, are independently authenticated and bound to the same immutable episode version; otherwise restart the download. Stage and validate shared schema, safe paths, size and SHA-256 before publication using the existing completion-marker design; reject duplicate IDs and preserve existing library and phone-local progress on any failure. Integrity digests do not authenticate a source.
5. PC displays paired devices and offers per-device revoke; atomically invalidate its verifier immediately, close its active streams and reject all subsequent requests, including reconnects. Phone offers forget, deleting its token and pin locally; this does not revoke the PC record if offline, so instruct the user to revoke on the PC too. Expiry requires a new physical ceremony and PC acceptance; no silent refresh. Disabling the listener closes connections and invalidates pending requests, but retains unexpired approved-device verifiers until revoke or expiry. A stolen bearer can be replayed by an admitted on-link attacker until expiry/revocation; TLS prevents passive capture, not replay after endpoint compromise. No claim of proof-of-possession for phone tokens.

## Rotation, errors and resource limits

Changed, lost, compromised or expired PC key/certificate: stop listener, revoke all device tokens, delete the old key as appropriate and generate a new certificate; every phone forgets its old identity and performs the full physical ceremony and fresh PC acceptance. No automatic pin replacement, grace period, insecure override or secret transmission to a changed identity. Store identity and verifier data together with restrictive permissions; loss, corruption or rollback of the local security store fails closed and requires rotation and re-pairing. Prevent rollback with an OS-protected monotonic mechanism or fail closed when freshness cannot be established; do not claim this property until demonstrated. Clock rollback or unreliable clock likewise disables token/certificate acceptance; monotonic deadlines bound active pairing.

Concrete initial ceilings, applied before allocation: 16 concurrent sockets total, 2 per source, TLS handshake 5 s, headers 8 KiB/5 s, JSON body 2 KiB/5 s, 10 failed pairing attempts per source per 15 minutes and 20 globally per 15 minutes, one pending ceremony globally, 2 polls/s, 30 s idle read timeout and 30 minute overall download deadline. Rate limits are global to the single listener, bounded in memory and fail closed on saturation; source-address limits are supplemental because addresses are spoofable/shared. Fixed windows and resets on restart permit bursts; require explicit re-enable after restart. Cap metadata/list response at 1 MiB, audio at 1 GiB, and staging at 2 GiB total; check actual bytes and advertised length, reject overrun, truncated, invalid or inconsistent lengths, and clean abandoned staging without removing published data. Enforce bounded concurrent streams and close them on deadline/revoke/network change. These limits mitigate, not eliminate, LAN denial of service; privileged local attackers remain out of scope.

Generic network errors must not disclose secrets, full request bodies, content or stack traces. Pairing rejection, invalid credentials and unknown routes must not expose device existence. A user-visible error distinguishes identity mismatch, expiry, network admission and storage failure locally without offering an insecure bypass. No request is retried automatically after ambiguous pairing issuance.

## Release gates (all outstanding)

- Independent security review of certificate-anchor behavior, QR provenance, approval race, token lifecycle, rollback protection and exact LAN admission on each supported OS; revise this design before implementation if any cannot be enforced.
- Controlled-server Android device tests prove pin and SAN/usage/validity verification occur before any HTTP bytes: wrong fingerprint, wrong IP/DNS SAN, expired/not-yet-valid or malformed cert, wrong key, changed cert, failed trust, hostile proxy, every redirect and DNS/network change. Capture traffic/server observations to prove no credential leak. Test SecureStore failure, backup/restore and uninstall behavior.
- Automated integration and actual device tests cover explicit PC accept/reject, timeout, concurrent/replayed issuance, response loss, revocation mid-stream and after reconnect, token expiry and rotation, non-LAN/forwarded/VPN/IPv4/IPv6/interface/firewall rejection, no broad API or legacy token access, rate/size/deadline limits and progress never uploaded.
- On device verify authenticated finished-episode download, corrupted/interrupted/duplicate import preserving library and progress, offline airplane-mode playback and restored position. T17/T19 stay unchecked until their full acceptance criteria and independent review pass.

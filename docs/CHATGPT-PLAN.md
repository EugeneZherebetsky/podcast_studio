# ChatGPT plan: experimental sign-in

In desktop Settings, sign in, load the signed-in account's available models, explicitly choose one, and select “Use ChatGPT for scripts”. The choice applies to new PC jobs. Only the script stage sends the local plan and research notes to OpenAI; planning, research, review and Piper stay local. The normal review still runs when enabled. The selected account must remain signed in and plan-enabled; if it expires or is signed out, jobs fail rather than falling back to another provider. Switch back explicitly with “Use local script generation”. A queued ChatGPT script is stopped before sending if the selection changes. Work already sent cannot be recalled. The published episode's existing generation LLM field identifies the ChatGPT script model, without the account label. There is no paid API fallback. The provider, account label and model are stored in a local JSON preference; credentials are not stored there or sent to the browser. An abrupt power loss may lose the most recent preference write. The selection intent file and crash-released SQLite lock coordinate current server processes; stop all older servers before upgrading because they do not observe this protocol.

Settings supports experimental sign-in when the server listens on numeric loopback and Settings is opened directly at that address (not via a proxy or Vite). Choose a label, start sign-in, then open the OpenAI link; cancel or sign out in Settings. If a provider choice fails or is interrupted, select a provider again before generating. Do not remove the selection lock or intent files while a server is running. Sign out before exiting: shutdown makes one short revocation attempt but may not be able to confirm it. See the next section for what happens when sign-out cannot be confirmed.

## Sign-out and the "could not confirm" warning

Rule: uncertainty exists only from the moment OpenAI may have issued tokens until either revocation is confirmed or the user states that they disconnected the app. Before the authorization code is sent to the token endpoint nothing has been issued, so starting, cancelling or failing a sign-in before that point leaves no trace.

Just before the code is sent, the server durably writes a grant record to `DATA_DIR/chatgpt/chatgpt-grants.json` (a crash-released SQLite mutex, temp file, fsync, atomic rename, strict schema and size cap as the registration file). Per-grant SQLite locks remain held while a process owns a live grant or a late exchange callback can still finish; acknowledgement keeps records owned by any process. SQLite lock files contain no tokens and must not be deleted while any server or CLI may be running. Before upgrading, stop **all** old server and CLI processes: old versions do not participate in the new locking protocol, and a legacy directory lock check cannot prevent every mixed-version race. If `chatgpt-registration.lock` exists, the new version refuses to proceed; only after confirming all old processes have stopped may an operator manually remove that directory. The lock is never automatically removed. If that write fails, the code is not sent and sign-in fails; an unredeemed code expires. A record holds only a random id, the account label, the issued client ID, a state (`grant-may-exist` or `revocation-unconfirmed`), a timestamp and, for access-only grants, the access-token expiry. It never holds tokens, codes, PKCE verifiers or authorization URLs. The record is removed when OpenAI answers the exchange with an error, or when revocation is confirmed at sign-out or shutdown. It becomes `revocation-unconfirmed` when the exchange fails in transit, times out or is cancelled mid-flight, or when revocation is not confirmed. While signed in, the record stays `grant-may-exist`; a process that stops without signing out leaves it behind.

Confirmation follows OpenAI's [End the renewable session](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#end-the-renewable-session): the refresh token is revoked at the discovery document's `revocation_endpoint`, and an HTTP 200 (including for an already-invalid token) confirms it. Network failures and 5xx responses are retried with backoff (up to four attempts, about 15 seconds overall); a 4xx is not retried and is not confirmation. Both refresh and access revocation must be confirmed: refresh revocation alone does not prove that an already issued access token is invalid. If refresh revocation is confirmed but access revocation is not, the warning persists until known access expiry; if refresh revocation is uncertain or a refresh token is malformed, expiry cannot resolve the grant uncertainty. This is stricter than the earlier refresh-only confirmation rule. Shutdown makes a single attempt bounded to about 3 seconds and applies the same rules. Tokens are cleared from memory whether or not revocation is confirmed.

Settings shows a warning whenever a record exists that does not belong to this process's own live session or sign-in in progress. It names the affected labels and says either "Podcast Studio stopped while signed in" (a `grant-may-exist` record left by a stopped process, or by another Podcast Studio process such as the CLI that is still signed in) or "Sign-out could not be confirmed". The warning does not mean the account was misused. To clear it, disconnect Podcast Studio in [ChatGPT Settings](https://chatgpt.com/settings/usage), which OpenAI's documentation names as the place to manage each app's access, then use "I've disconnected Podcast Studio in ChatGPT Settings" and confirm. This is the user's statement, not verification: the server only deletes its local records that are not owned by a live process (`POST /api/chatgpt/acknowledge` with `{"disconnectedInChatGptSettings": true}`, refused with 409 while signed in, signing in or signing out). After a confirmed sign-out Settings says the session was ended; per OpenAI, revoking a session does not delete the registered client.

None of this has been exercised against OpenAI: live sign-in, revocation and disconnection remain untested.

An experimental local CLI provides a separate sign-in and text inference session. Run `pnpm --filter server chatgpt`, then enter `login <label>` and open the displayed URL in a system browser; use `models` to list eligible models and `ask <model> <prompt>` to generate text. Results are shown only after completion, limited to 1 MB of stream data and 60 seconds; Ctrl-C cancels an active request. Use `status`, `signout`, and `quit` in the same process. Use a different label for another registration. Sign out before changing accounts. Only a stable opaque host ID, verified account/client mappings and token-free grant records are stored under `DATA_DIR/chatgpt`; configure DATA_DIR on private storage (the default `data/` is git-ignored). On Unix the new files use owner-only modes; on Windows they inherit the directory ACL, which the user must keep private. A stale `chatgpt-registration.lock` after a crash must be removed manually only after confirming no old server or CLI process is running. Tokens remain in process memory; quitting makes one short revocation attempt, and an unconfirmed or crashed session leaves a grant record that Settings reports. Signout attempts remote revocation with retries and warns if it could not confirm it. No tokens are sent to the browser. Local Ollama remains unchanged; there is no paid API fallback.

OpenAI documents [ChatGPT plan usage for locally hosted open-source apps](https://developers.openai.com/siwc/token-sharing-open-source), including [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), and [UX](https://developers.openai.com/siwc/ui-ux-guidelines). The isolated login uses fresh state, nonce and S256 PKCE, bounds the listener and exchange, and verifies RS256 signatures and identity claims with `jose` and OpenAI's JWKS. Granted token-response scopes determine plan permission; a verified identity alone is insufficient.

## Experimental script draft

In the same CLI session, use `models`, then `script <model-slug> <research.json>`. The UTF-8 JSON file contains `{ "mode": "standard", "lang": "en", "plan": {...}, "notes": {...}, "sources": {...} }`, using the existing pipeline's `PlanSchema`, `NotesSchema`, and `SourcesSchema` (`apps/server/src/pipeline/schemas.ts`). Prepare these research artifacts separately; this command does not search the web. It sends the plan and notes to ChatGPT and prints a validated script with `reviewed: false`; it does not modify the input or write an episode. Review the result and its sources before use. Factual support is not established by schema validation. Review, TTS, publishing, retries and pipeline caching are not connected.

The command requests JSON schema output and validates the completed response locally, including citation IDs and word budget. Plan inference documentation does not establish structured-output compatibility; if the service rejects this request the command fails rather than falling back to unstructured text or a paid API. No live compatibility test has been performed. Input research is sent to OpenAI only when the user runs this command.

Before pipeline generation integration: review authorization to send data and shared config/schema changes; implement refresh serialization. Never expose credentials or PKCE verifiers to browser-accessible APIs or logs. Request/response size and time bounds, cancellation, local process threats, and callback origin/Host handling require continuing security review.

Windows credential protection is unresolved. Node's Unix mode bits alone do not establish a private Windows ACL. Evaluate OS-backed storage such as [Windows Credential Manager or DPAPI](https://learn.microsoft.com/en-us/windows/win32/secbp/threat-mitigation-techniques); any new native dependency requires separate approval. Do not persist tokens in plaintext as a workaround.

The existing pipeline requires Zod-validated structured objects and retry/usage accounting. OpenAI's plan-usage docs require streaming Responses with `store: false`, `stream: true`, and `response.completed`; several normal Responses parameters are unsupported. The plan-specific documentation reviewed does not establish structured-output support for this route, so that compatibility must be verified without assuming ordinary API behavior. Discover account-eligible models rather than hardcoding them. Enforce size/time limits, validation and no tool access to untrusted sources. Implement plan-limit messaging and usage links per OpenAI's UX requirements, without automatic paid fallback. No live login or inference has been performed.

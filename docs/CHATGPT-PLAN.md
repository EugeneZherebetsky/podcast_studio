# ChatGPT plan: not yet available

The settings page reports the current status; it does not offer sign-in or generation. The isolated server-side OAuth preparation and identity-verification modules are not connected to the app. They do not implement a complete OAuth client, store credentials, or initiate network calls by themselves; the verifier would fetch OpenAI's JWKS if invoked without a test key set. Local Ollama remains unchanged. A ChatGPT subscription is not an OpenAI API key; there is no paid API fallback.

OpenAI documents [ChatGPT plan usage for locally hosted open-source apps](https://developers.openai.com/siwc/token-sharing-open-source), including [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), and [UX](https://developers.openai.com/siwc/ui-ux-guidelines). This foundation prepares a dynamic registration request with fresh state, nonce and S256 PKCE and validates a callback target; a separate verifier checks RS256 signatures and identity claims with `jose` and OpenAI's JWKS. Neither is integrated into a complete sign-in flow, and a verified identity alone does not establish plan permission.

Before integration: review authorization to send data and shared config/schema changes; persist one stable opaque host ID per host; bind a time-limited listener exclusively to IPv4 loopback before opening the system browser; protect pending attempts against concurrent and replayed callbacks; exchange only at the official endpoint; validate ID-token signature, issuer, audience, expiry and nonce against OpenAI JWKS, identity binding and granted scopes; implement account separation, refresh serialization and revocation. Never expose credentials or PKCE verifiers to browser-accessible APIs or logs. Request/response size and time bounds, cancellation, local process threats, and callback origin/Host handling require security review.

Windows credential protection is unresolved. Node's Unix mode bits alone do not establish a private Windows ACL. Evaluate OS-backed storage such as [Windows Credential Manager or DPAPI](https://learn.microsoft.com/en-us/windows/win32/secbp/threat-mitigation-techniques); any new native dependency requires separate approval. Do not persist tokens in plaintext as a workaround.

The existing pipeline requires Zod-validated structured objects and retry/usage accounting. OpenAI's plan-usage docs require streaming Responses with `store: false`, `stream: true`, and `response.completed`; several normal Responses parameters are unsupported. The plan-specific documentation reviewed does not establish structured-output support for this route, so that compatibility must be verified without assuming ordinary API behavior. Discover account-eligible models rather than hardcoding them. Enforce size/time limits, validation and no tool access to untrusted sources. Implement plan-limit messaging and usage links per OpenAI's UX requirements, without automatic paid fallback. No live login or inference has been performed.

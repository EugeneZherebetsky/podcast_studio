# Local transfer threat model and implementation gates

Status: design input only. No transfer transport, credential store, pairing or LAN listener is enabled by this document. T17 and T19 remain open; independent security review and device verification are required before use.

## Assets and trust boundaries

Assets are the PC's TLS private key and identity, pairing material and per-device credentials, episode metadata and audio, and the phone's local library and learning progress. Boundaries cross from the PC user to the phone user (initial identity), from untrusted discovery/network traffic to both devices, from the transfer listener to episode data, and from app storage to credentials. A home LAN, its DNS, other connected devices, VPNs, proxies and the network's routing are not inherently trusted. A compromised endpoint or malicious person with legitimate device access is outside the protection of TLS; endpoint access controls remain necessary.

## Abuse cases and required controls

- **Spoofing and disclosure:** An attacker advertises a substitute PC or intercepts traffic. The phone must authenticate the PC identity out of band before transmitting *any* pairing material or reusable credential. The approved full-certificate SHA-256 fingerprint must be checked during the handshake for that connection, alongside normal hostname/IP SAN verification, certificate validity and proof of private-key possession. Wrong, changed, expired, or absent identity must fail closed. Rotation and recovery require fresh out-of-band verification, not automatic trust-on-first-use. The precise out-of-band ceremony is not yet specified or reviewed.
- **Tampering:** Metadata and audio must come through the authenticated connection; package hash and schema validation detect corruption or inconsistency but do not establish PC identity. Stage and verify before publication, preserving existing library and progress on failure.
- **Credential leakage and redirect:** Do not send secrets before peer verification, through a proxy, in URLs, logs, redirects, error messages, or to another host. Disable redirects and proxy use per connection. Tests must establish that mismatched certificates, hostname and redirect paths do not disclose a credential. No progress or vocabulary upload.
- **Authorization and privilege escalation:** The LAN listener must be separate, explicitly enabled, off by default and never proxy the management API. Explicit PC approval, denial, expiration and revocation per phone are required. Authorize every request and serve only finished episode reads. Legacy pairing/tokens and sync routes are not a basis for this listener.
- **Denial of service:** Limit connections, operation time, request/response sizes, pairing attempts and staging storage; reject invalid lengths and incomplete responses. Preserve existing files on failure. Timeouts alone are not necessarily an end-to-end deadline.
- **Repudiation and privacy:** Record approval/revocation decisions without recording credentials or private content. Define retention and deletion; no telemetry or cloud service is introduced.
- **Network boundary:** Private IP ranges alone do not establish home-network admission. Explicitly design multi-interface, VPN, IPv4/IPv6, firewall and network-change handling; prevent public exposure or forwarding. A TLS pin alone does not enforce home-LAN-only access.

## Native feasibility and unresolved protocol

[Expo local-module documentation](https://docs.expo.dev/modules/get-started/) describes a local `modules/` directory and native rebuild; [module configuration](https://docs.expo.dev/modules/module-config/) registers the Android Kotlin class. [Android TLS guidance](https://developer.android.com/privacy-and-security/security-ssl) warns against trust-all managers and states that `HttpsURLConnection` verifies certificates and hostnames. [Android SSLParameters](https://developer.android.com/reference/javax/net/ssl/SSLParameters#setEndpointIdentificationAlgorithm(java.lang.String)) documents endpoint identification for TLS sockets. These descriptions are not proof that a proposed runtime pin implementation behaves correctly on supported Android versions. In particular, sending an HTTP request or authorization header before validating the pin is not acceptable, and changing global trust, hostname verification, or proxy state is not acceptable.

[Expo SDK 58 SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/) uses Android Keystore-backed encryption and documents Android backup exclusions and uninstall behavior. It is not an authorization mechanism or an authenticated pairing ceremony, and its native behavior requires device testing. Do not store credentials in SQLite, AsyncStorage, URLs, logs, tracked files or as a fallback when secure storage fails.

The exact listener protocol, pairing state machine, out-of-band verification ceremony, credential lifecycle and endpoint paths have not been specified or reviewed. The existing broad desktop API and legacy pairing cannot safely fill those gaps. A native implementation must not invent a generic credential-bearing HTTP API or become reachable from the app while those decisions are unresolved. Before implementation, review the ceremony and define narrowly scoped operations and limits; then test the actual Android TLS implementation with a controlled server and device, including wrong fingerprint, wrong SAN, expiry, redirect/no credential leak, proxies, timeout and response bounds. Device acceptance/rejection, revocation, LAN admission and offline download checks remain separate gates.

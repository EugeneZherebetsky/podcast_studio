# Write-only key-entry prototype — disabled

This slice is **not imported by the desktop shell**, does not start or restart the server, and does not supply stored values to any process. Use synthetic values only. It has no read API: the dedicated local entry window can list presence, set, and clear allowlisted provider keys; ChatGPT session tokens are not accepted. Input necessarily exists briefly in the isolated key-entry renderer; it is never sent to the existing web renderer, HTTP server, dotenv, logs, or child by this code. Stored changes are staged only, not active. No restart button is provided. Any future application of changes requires a separate manual safe restart after guard-safe shutdown; no such activation exists here.

Run `node --test apps/desktop/write-only-store.test.mjs apps/desktop/supervisor.test.mjs` and, on Windows after installing the existing locked dependencies, `pnpm exec electron apps/desktop/write-only-smoke.mjs`. The Electron probe uses a temporary profile, synthetic input, a real sandboxed preload and Windows DPAPI. It exercises authorized entry, an untrusted sender, window lifecycle and setup failures; a fake storage backend checks the capacity boundary with synthetic values. Windows may retain temporary Chromium profile files in the scratch directory when they are locked at exit; the synthetic key file is removed. Tests do not touch the real profile or start the application server.

The store rejects corruption instead of replacing it, rejects encrypted blobs over 131072 bytes before creating a temporary file, and writes accepted encrypted data to a new same-directory temporary file, flushes it and renames it over the old file. A cooperative lock directory serializes separate store instances and processes; a crash can leave a lock requiring manual recovery after confirming no owner is running. Never automatically delete a lock merely because it is old. Parent junctions and existing link targets are rejected, but path checks are not race-proof against another process running as the same user. Windows ACLs, reparse-point races, safe lock recovery, unusual filesystems and power-loss durability are not proven. DPAPI does not protect data from other processes running as the same Windows user.

Only one key window may be open or opening at a time; a repeated request is rejected. Closing it releases its IPC handlers so a later window can open. Setup failures destroy the new window and remove only handlers registered by that attempt.

Before integration or use with real credentials, resolve all gates in `D5-BLOCKERS.md`, including provider/error/event/database/stdout redaction and safe shutdown/admission semantics. Review the IPC boundary including subframes/navigation, multiple windows, session permissions, CSP and packaged resource integrity. Electron recommends avoiding `file://`; the isolated prototype uses a local file with strict sender identity and CSP, so a reviewed custom protocol is an additional integration gate. Independently verify symlink/reparse attacks and file replacement/durability on supported Windows filesystems. Do not use this prototype as proof that credential injection is safe.

References: [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) and [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security); [sandboxed preload](https://www.electronjs.org/docs/latest/tutorial/sandbox#preload-scripts).
